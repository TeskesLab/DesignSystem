# Rust / egui and GPUI Kit libraries

`rust/` contains the reusable `teskeslab-design-system` crate with optional **egui 0.33.x** and **GPUI Kit 0.8.1** adapters. Both consume the same canonical generated tokens and bundled fonts. Publication to crates.io is manual; see the [Cargo release procedure](16-cargo-release.md). Preparing or checking the crate does not publish it.

## Dependency and initialization

Rust 1.92 or newer is required; the GPUI Kit Linux dependency graph includes `oo7` 0.6 (see [official installation requirements](https://gpui-kit.com/docs/installation)). Features are additive, with **no default features**:

| Features | Public API / dependencies |
| --- | --- |
| none (default) | `no_std` tokens and font bytes; no GUI dependencies |
| `egui` | `teskeslab_design_system::egui`, egui 0.33 |
| `gpui-kit` | `teskeslab_design_system::gpui`, GPUI Kit 0.8.1 |
| `egui,gpui-kit` | Both adapters in one crate; neither replaces the other |
| `egui-showcase` | egui adapter plus eframe/PNG example dependencies |
| `gpui-showcase` | GPUI Kit adapter and its desktop/headless capture example |
| `gpui-test-support` | GPUI Kit native test/headless support; enabled by `gpui-showcase` |

The old `native` module and `showcase` feature are removed: migrate imports to `teskeslab_design_system::egui` and select `egui-showcase` for the eframe example.

### egui initialization

A local egui consumer can use:

```toml
[dependencies]
teskeslab-design-system = { path = "../DesignSystem/rust", features = ["egui"] }
egui = "0.33"
```

Initialize fonts once, normally in the application's creation callback. Apply the theme at initialization and when the resolved preference changes, not every frame:

```rust
use teskeslab_design_system::{Density, Scheme};
use teskeslab_design_system::egui::{self as design, Theme};

fn configure(ctx: &egui::Context) {
    design::install_fonts(ctx);
    Theme {
        scheme: Scheme::Dark,
        density: Density::Comfortable,
        touch: false,
    }.apply(ctx);
}
```

`Theme::apply` sets the explicit egui theme and updates the existing style for that scheme. The application owns preference storage and System → OS preference → light fallback resolution. `Theme::map_style` preserves unrelated style settings; use it for an existing style, or customize the result of `Theme::style`. The theme does not override application zoom/pixels-per-point. Retain one `Theme` value in application state and pass it to helpers so controls and global styling agree.

`egui::add_fonts(&mut FontDefinitions)` is the alternative when an application already has custom fallback fonts. It prepends Plex without duplicating family entries or removing fallback glyph coverage. `install_fonts` starts with egui's built-in fallback definitions. Do not call either every frame: font installation can rebuild the atlas.

For a dependency-free, `no_std` token/font library (also the default):

```toml
[dependencies]
teskeslab-design-system = { path = "../DesignSystem/rust", default-features = false }
```

This keeps `tokens`, typed `Scheme`, `Role`, `Density`, `Rgba`, `Metrics`, `color`, `dimensions`, and `fonts` available. No egui, GPUI Kit, eframe or PNG dependency is enabled. `Role::ALL` and `Role::name` provide discoverability without allocating a map. Generated colors and metrics are immutable, exhaustive typed values. `src/tokens.rs` and font assets are generated by the repository's native asset generator; do not maintain a separate palette in this crate.

## egui mapping

| Native role | Canonical mapping |
| --- | --- |
| Panel / window / input background | surface-page / surface-raised / surface-raised |
| Input boundary / decorative boundary | control-border / border-subtle |
| Body / secondary text | text-primary / text-secondary |
| Hover / selected surface | surface-hover / surface-selected |
| Focus stroke | focus-ring, canonical focus width |
| Link / warning / error | text-link / status-warning-text / status-danger-text |
| Code background | code-bg; use code-text explicitly for technical-value labels |
| Selection | surface-selected with text-primary foreground |
| Primary and danger actions | paired normal, hover, pressed and text roles |
| Status helpers | corresponding paired status background and text |

Regular text uses real IBM Plex Sans 400. Headings, buttons and `egui::strong_family()` use the bundled IBM Plex Sans SemiBold 600; `RichText::strong()` alone is not a request for that face. Monospace uses IBM Plex Mono 400. There is no italic or monospace-bold asset: do not claim those weights/faces are supplied or silently synthesize them. A product needing those faces must add reviewed, licensed fonts. Existing glyph fallbacks are retained but may have different metrics and weight.

The built-in egui text styles map Heading to section size, Body to body size, Button to UI size, Small to meta size, and Monospace to UI size. Other canonical type sizes are available as tokens for explicit `FontId` values. egui's layout engine determines line metrics; CSS leading, weight synthesis and browser pixel identity are not promised.

Spacing and button padding follow canonical metrics. Control height is a **minimum**, not a fixed clipping rectangle. Compact mode reduces controls; `touch: true` restores comfortable targets even when density is compact. Table/list builders must apply `theme.metrics().row_height` explicitly. Standard egui widgets retain toolkit sizing conventions; a TextEdit or custom widget can need a larger product-specific hit area. Dialog content should use comfortable controls. Badges use the reference's 13-point regular text and 3-point corners; callouts use UI text, canonical spacing and a 3-point leading accent.

## Actions and status helpers

```rust
use teskeslab_design_system::egui::{self as design, ActionKind, ActionState, Theme};

fn controls(ui: &mut egui::Ui, theme: Theme, busy: bool, can_apply: bool) -> bool {
    design::action(
        ui,
        theme,
        ActionKind::Primary,
        "Apply changes",
        ActionState { disabled: !can_apply, busy },
    ).activated()
}
```

- `ActionKind` provides Primary, Secondary, Quiet and Danger variants through a native egui Button. Native pointer, Tab, Enter/Space and AccessKit activation behavior stays with egui; no global/default Enter handler is installed.
- `ActionResponse::activated()` guards the native click with disabled/busy state and inherited parent enablement. Use it at dispatch. Backend deduplication and authorization remain the application's responsibility.
- Busy changes the native sense to focusable/noninteractive, so an already-focused action retains focus but pointer/keyboard/AccessKit clicks cannot dispatch. The label and geometry remain stable, with an inset busy underline. Keep persistent adjacent text naming the operation and its state; the underline is not a measured-progress indicator and is not sufficient status feedback on its own.
- Disabled uses the native disabled-input path. Disabled/busy helpers use paired disabled colors, and an extra focus ring is drawn when focused. Standard egui controls still use egui's general disabled-opacity behavior rather than a claim of exact per-widget disabled tokens.
- Helpers restore their temporary visual mapping, so a primary/danger button does not recolor subsequent fields or labels. They do not allocate/copy an entire style/font map for every button.
- Labels may wrap and dimensions grow with content. Action groups should use `horizontal_wrapped` on narrow layouts. Separate destructive actions and use explicit wording, not merely red color.
- `badge(ui, theme, status, text)` is noninteractive text; `callout(ui, theme, status, title, body)` is persistent wrapping text. `Status` covers Success, Warning, Danger, Info and Neutral. Text conveys meaning independently of color.

Use standard egui text fields, labels, checkboxes, menus, tables and dialogs directly. The showcase demonstrates a text edit linked with `labelled_by`; it does not add a parallel field/form framework. Product validation must associate error text and preserve input. The library does not invent live-region announcements, dialog focus trapping, job state machines, or accessibility certification. AccessKit must be enabled/configured in the host integration and tested with actual platform assistive technology. The showcase enables eframe's AccessKit integration, but that alone is not evidence of screen-reader conformance.

## egui interactive showcase and native screenshot smoke

From the repository root:

```sh
cargo run --manifest-path rust/Cargo.toml --example showcase --features egui-showcase
```

The real eframe window supports both schemes and densities, touch targets, pointer/keyboard counter activation, guarded disabled/busy buttons, a local busy toggle, reset/clear actions, native form controls, paired status labels, callout text and selectable technical values. The busy toggle is explicitly local UI state; it does not simulate a background operation or invent progress.

For deterministic integration evidence:

```sh
cargo run --manifest-path rust/Cargo.toml --example showcase --features egui-showcase -- --smoke /tmp/teskeslab-rust-smoke
```

Smoke mode renders all four light/dark × comfortable/compact combinations. It injects native egui pointer input to the real button rectangles, verifies a counter activation, attempts disabled and busy actions, then focuses the primary button and injects Enter. Assertions require exactly two successful activations and no blocked dispatches per variant. Each variant requests `ViewportCommand::Screenshot`, encodes the returned actual native frame as PNG, and exits after four images:

- `light-comfortable.png`
- `light-compact.png`
- `dark-comfortable.png`
- `dark-compact.png`

No hand-painted mock screenshots or external mouse automation are used. Capture failures or missing responses fail rather than reporting synthetic success. This exercises integration input and pixels; it does not replace OS keyboard routing, assistive technology or visual review.

Linux headless example (Xvfb, Mesa software GL and xauth installed):

```sh
LIBGL_ALWAYS_SOFTWARE=1 xvfb-run -a -s '-screen 0 1280x1100x24' \
  cargo run --manifest-path rust/Cargo.toml --example showcase --features egui-showcase -- --smoke /tmp/teskeslab-rust-smoke
```

The optional `egui-showcase` feature enables eframe 0.33 with Glow, X11, Wayland and AccessKit, plus image 0.25 with PNG encoding only. Normal library use does not require eframe or image. Linux desktop execution needs a working X11/Wayland display and OpenGL/EGL/GLX driver; distro development/runtime packages commonly include a C linker, pkg-config, libxkbcommon, Wayland libraries, X11 libraries and Mesa GL/EGL. Exact package names vary by distribution. Tokens-only and headless egui input tests do not require a display server.

On a Wayland desktop, unset `WAYLAND_DISPLAY` and `WAYLAND_SOCKET` when selecting an Xvfb display, otherwise winit may still select Wayland. NixOS execution also needs the dynamically loaded X11/OpenGL libraries on the runtime library path; the repository smoke was run in a Nix shell providing `libGL`, `libxkbcommon`, `libx11`, `libxcursor`, `libxi`, `libxrandr`, `libxinerama` and `mesa`.

## GPUI Kit dependency and runtime

Enable only the toolkit you need, or request both adapters explicitly:

```toml
[dependencies]
teskeslab-design-system = { path = "../DesignSystem/rust", features = ["gpui-kit"] }
gpui-kit = "=0.8.1"
# To use both adapters, change the first feature list to ["egui", "gpui-kit"].
```

The GPUI Kit adapter is `teskeslab_design_system::gpui`; the toolkit dependency is `gpui_kit`. Its theme uses the shared `Scheme`, `Density` and `touch` preference inputs. Install bundled fonts during application initialization and update the theme when preferences change. Keep application jobs, navigation, preference persistence and error reporting in the consumer.

```rust
use teskeslab_design_system::{Density, Scheme};
use teskeslab_design_system::gpui::{self as design, Theme};

fn configure(cx: &mut gpui_kit::App) -> gpui_kit::Result<()> {
    design::init(cx, Theme {
        scheme: Scheme::Dark,
        density: Density::Comfortable,
        touch: false,
    })
}
```

`gpui::init` initializes the kit, registers the bundled Plex fonts and applies the theme. Propagate its font-registration error rather than silently replacing the fonts. Later preference changes use `Theme::apply`. `Theme::map_colors` maps an existing component theme color set; `Theme::color(Role)` exposes every canonical role for custom elements.

Kit density is explicit, not a global zoom adjustment: use `Theme::control` and `Theme::row` for custom controls/rows, or the adapter's `action` and `input` helpers, which apply the corresponding metrics. Touch mode restores comfortable target sizes even at compact density. Toolkit-derived component shades and layout metrics can differ from the web reference; do not claim pixel identity.

`action` returns a native kit Button, preserving toolkit focus/input behavior with a guarded callback. Busy/loading keeps focus but blocks dispatch; disabled buttons leave the tab order. Busy is application-owned state, not a fabricated operation or progress estimate. `input` uses a native `InputState`; `status` uses a native Alert with text and paired status colors. Keep labels/errors visible and associated with their controls, preserve field content, and test real platform keyboard and assistive-technology behavior rather than treating toolkit support as accessibility certification.

Danger actions use `ActionDanger*` roles; danger status alerts instead use `StatusDangerBg`/`StatusDangerText`. These are deliberately distinct palettes. Kit derives some interaction shades and focus geometry internally; use `Theme::color` for explicit code, navigation and other semantic roles not directly exposed by component theme slots.

GPUI Kit is a real desktop dependency, not a browser renderer or an egui wrapper. See its [official installation guide](https://gpui-kit.com/docs/installation) for platform-specific requirements. Linux rendering requires a working Vulkan driver; Mesa software Vulkan is acceptable for smoke evidence but does not establish production GPU behavior. A desktop example also needs a working display session.

On NixOS, from the repository root, use the supplied native dependency shell (it uses the caller's Rust toolchain):

```sh
nix-shell rust/shell.nix --run 'cargo check --manifest-path rust/Cargo.toml --all-features --all-targets'
nix-shell rust/shell.nix --run 'cargo run --manifest-path rust/Cargo.toml --example gpui_showcase --features gpui-showcase'
```

On network mounts that reject Rust metadata links (`Operation not permitted` / invalid `.rmeta`), place Cargo outputs on a local filesystem before these commands:

```sh
export CARGO_TARGET_DIR="${XDG_CACHE_HOME:-$HOME/.cache}/teskeslab-design-system/target"
```

Token-only and core egui tests do not need this shell. The GPUI Kit dependency is not compiled when only `egui` or no features are selected. Cargo feature unification is additive: a downstream dependency enabling GPUI Kit will still enable it for that resolved crate instance.

For real offscreen Vulkan captures across both schemes, both densities and touch on/off:

```sh
nix-shell rust/shell.nix --run 'cargo run --manifest-path rust/Cargo.toml --example gpui_showcase --features gpui-showcase -- --smoke validation/native/gpui'
```

The example writes eight `gpui-{Light|Dark}-{Comfortable|Compact}-touch-{false|true}.png` images. Without an output directory, smoke uses `target/gpui-smoke`. It advances the headless clock before capture so native checkmark animations reach their target. Unsupported platforms or renderer failures return errors rather than synthetic screenshots. See the [verification record](../tests/README.md#native-libraries) for exercised checks and their limits.

## Verification commands

Run after generated tokens/fonts and all implementation changes have landed:

```sh
cargo test --manifest-path rust/Cargo.toml --no-default-features
cargo test --manifest-path rust/Cargo.toml --features egui
cargo test --manifest-path rust/Cargo.toml --features gpui-kit
cargo test --manifest-path rust/Cargo.toml --features egui,gpui-kit
cargo test --manifest-path rust/Cargo.toml --all-features
cargo check --manifest-path rust/Cargo.toml --all-features --all-targets
cargo fmt --manifest-path rust/Cargo.toml -- --check
cargo clippy --manifest-path rust/Cargo.toml --all-features --all-targets -- -D warnings
```

The tests cover semantic contrast, role uniqueness, touch-over-compact targets, egui font fallback/style isolation, and real toolkit input, activation guards, keyboard focus and density transitions. GPUI interaction tests require `gpui-test-support` (also enabled by `--all-features`); plain `gpui-kit` builds do not enable toolkit test instrumentation. Run native smoke separately and inspect both sets of PNGs, then exercise text zoom, narrow windows and actual assistive technology. Commands here are instructions, not a claim of platform-wide conformance.
